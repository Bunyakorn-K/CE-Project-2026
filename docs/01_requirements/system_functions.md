# ⚙️ System Functions (Functional Decomposition)

**Document Purpose:** This document defines the core functional capabilities of the LaundryTwin platform, outlining the technical details, acceptance criteria, and security constraints. These functions trace back to the project's Quantifiable Requirements (QR) — see [`house_of_quality.md`](house_of_quality.md) Step D for the QR specs.

| ID       | Category        | Function Name                      | Technical Details                                                                                                                   | Use Case                                                                                          | QR (house_of_quality.md) | Phase     | Acceptance Criteria                                                                          | Constraints / Security                                                                 |
| :------- | :-------------- | :--------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ | :---------------------- | :--------- | :------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **F-01** | Digital Twin    | Virtual Presence & State Sync      | Display machine state, remaining time, and temp from a versioned register map; reject unmapped or stale values.                     | **Remote Diagnostics:** Manager sees the accurate, latest physical status of the machine.         | QR-01                  | **MVP**   | Displays the latest valid status within 2 seconds at p95 post-ingestion.                     | Do not claim 100% real-time; UI must display the last updated timestamp.               |
| **F-02** | Gas Management  | Estimated Gas Remaining            | Estimate low gas trends using pressure, temperature, and usage history, with configurable confidence thresholds.                    | **Gas Planning:** Manager receives an early warning before dryer service is disrupted.            | QR-04                  | **MVP**   | Generates a unique alert with evidence when the low-gas threshold is met.                    | Requires a physical gas-leak detector for leak alerts; pressure alone is insufficient. |
| **F-03** | Digital Twin    | Spatial Layout & Error Correlation | Optional floorplan UI displaying machine locations overlaid with verified status/anomaly data.                                      | **Zone Diagnostics:** Technician visually identifies anomalies clustered in specific areas.       | — (Phase 2, no QR yet)  | _Phase 2_ | Every machine is mapped to a floorplan coordinate and data timestamp.                        | Do not assume root cause based purely on spatial correlation.                          |
| **F-04** | Infrastructure  | Telemetry Data Streaming           | Push normalized telemetry to authenticated clients via WebSocket or SSE, with auto-reconnect handling.                              | **Real-time Monitoring:** Dashboard remains open and updates seamlessly without refreshing.       | QR-01                  | **MVP**   | Client receives valid events within latency targets and successfully reconnects after drops. | Verify subscription authorization strictly by role and branch.                         |
| **F-05** | Infrastructure  | MQTT Ingestion & Data Pipeline     | Validate payload schema, normalize units, enforce `branch_id`/`machine_id`/`register_map_version`, deduplicate, and store data.     | **Data Foundation:** Multiple branches stream telemetry reliably into a centralized pipeline.     | QR-02                  | **MVP**   | Invalid payloads are quarantined with reasons; valid payloads are stored idempotently.       | Never expose MQTT credentials or raw payloads to public clients.                       |
| **F-06** | Infrastructure  | Role-Based Access Control (RBAC)   | Utilize authenticated sessions/JWTs and tenant-aware queries; strictly enforce roles and branch IDs server-side.                    | **Franchise Security:** Owners and Managers are strictly limited to their authorized data scopes. | QR-03                  | **MVP**   | Automated tests confirm unauthorized cross-branch API requests are denied.                   | Frontend filtering alone does NOT constitute authorization.                            |
| **F-07** | Infrastructure  | Authentication & Audit Log         | Authenticate users, store password hashes securely, and write append-only audit events for critical settings and AI tool calls.     | **Security Traceability:** Owner can audit exactly who modified alert settings.                   | QR-03                  | **MVP**   | Audit events include actor, action, target, timestamp, and outcome.                          | Protect system secrets and minimize PII storage.                                       |
| **F-08** | Business Logic  | KPI Aggregation & Data Export      | Aggregate gross revenue, cycles, and utilization from normalized events by branch/time; export approved summaries.                  | **Financial Summary:** Owner exports monthly operational summaries for accounting.                | QR-02, QR-03           | **MVP**   | Selected dashboard aggregates are fully traceable to source events within the timeframe.     | Explicitly specify "gross revenue"; do not present as net profit without cost data.    |
| **F-09** | Business Logic  | Estimated Coin-Box Fill & Reset    | Calculate volume estimates using calibrated cash/coin events; allow resets ONLY via explicitly mapped `coinbox_open` events.        | **Revenue Protection:** Manager collects coins before physical capacity is reached.               | QR-04                  | **MVP**   | Resets must generate an audit record and cannot be triggered by unmapped door statuses.      | Capacity and event mapping are fixed configurations, not assumptions.                  |
| **F-10** | Business Logic  | Event-Driven Alert Engine          | Evaluate versioned rules, apply cooldown windows for deduplication, and dispatch messages via LINE Messaging API.                   | **Proactive Maintenance:** Technician receives immediate alerts for problematic machines.         | QR-04                  | **MVP**   | Maximum one alert per rule/entity/cooldown window; delivery results are logged.              | LINE Notify is deprecated; must use Official Account and protect channel credentials.  |
| **F-11** | AI Integration  | Safe Analytics Function Calling    | Parse user intent to allow-listed analytics functions; backend strictly verifies arguments, RBAC, and branch scope before querying. | **Smart Executive Report:** Owner asks for a MoM comparison of authorized branches.               | QR-05                  | **MVP**   | System logs the prompt, tool name, sanitized arguments, and result reference.                | The LLM is strictly prohibited from generating or executing arbitrary SQL.             |
| **F-12** | AI Integration  | External Context (Weather API)     | Normalize branch locations and times; correlate weather data exclusively for specified analysis periods.                            | **Demand Analysis:** Report correlations between weather patterns and machine usage.              | — (Phase 2, no QR yet)  | _Phase 2_ | Output specifies the source data range and explicitly states correlation limits.             | Do not claim causation or forecasting accuracy without proper validation.              |
| **F-13** | Customer Facing | Public Machine Status API          | Serve machine availability and remaining time via a read-only, aggressively rate-limited endpoint.                                  | **Customer Convenience:** LIFF/web view allows customers to check if machines are free.           | QR-03                  | _Phase 2_ | Response schema strictly excludes revenue data, raw MQTT telemetry, or internal branch info. | Use public-specific DTOs and rate limits; do not expose internal APIs.                 |

*Phase is a commitment level, not a delivery status.* F-12 (weather) shipped
ahead of its phase, F-02 and F-07 are partial, F-09 is blocked upstream, and
F-04/F-05 were descoped or replaced. Delivery evidence lives in the requirement
status table in [`system_requirement.md`](system_requirement.md#implementation-status-verified-2026-09-14-r06-re-checked-2026-09-30)
and in [`RTM_matrix.md`](../04_traceability/RTM_matrix.md) — it is not repeated
here, so the two cannot disagree.

*QR column maps each function to the Quantifiable Requirement(s) it serves,
defined in [`house_of_quality.md`](house_of_quality.md) Step D. `— (Phase 2, no
QR yet)` means the capability is a declared target without a committed
measurable goal at this stage (F-03, F-12). The F-IDs and priorities below are
the operational source of truth and are not renumbered.*
