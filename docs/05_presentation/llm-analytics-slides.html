แบบที่ไม่เอา Blackbox

โยนคำถาม + ข้อมูลดิบ (หรือสิทธิ์ query ฐานข้อมูล) ให้ LLM แล้วหวังว่าจะตอบถูก

• ตัวเลข หลอน (hallucination) ตรวจย้อนกลับไม่ได้
• LLM เขียน SQL เอง = ช่องโหว่ข้ามสาขา / ข้ามสิทธิ์
• ข้อมูลดิบยาวเกิน context และเปลืองต้นทุน
• ตอบไม่เหมือนเดิมทุกครั้ง (non-deterministic)
• ไม่มีหลักฐานว่าใครถามอะไร ระบบตอบจากอะไร

ภาพรวมระบบ

ข้อมูลเดินทางจากเครื่องซักผ้า ถึงคำตอบผู้บริหารอย่างไร

ส่วนสีเข้มคือของใหม่ที่เพิ่มในหัวข้อนี้ ส่วนที่เหลือคือฐานที่ระบบมีอยู่แล้ว

1. Edge / IoT

เครื่องซักผ้าส่ง Modbus frame → telemetry event ทุก event ต้องมี branch_id และ machine_id

2. Ingestion

ตรวจ schema, ปฏิเสธ branch_id ที่ไม่รู้จัก, แปลงเป็น MACHINE_CYCLE และหลักฐานการชำระเงิน

3. Rollup ใหม่

สรุปล่วงหน้าเป็นราย “ชั่วโมง / วัน × สาขา × เครื่อง” เก็บเป็นตารางสรุปพร้อมใช้

4. Analytics Functions ใหม่

ฟังก์ชันสถิติแบบ parameterized ที่ allow-list ไว้ คืนค่าเป็น envelope มาตรฐาน

5. Assistant Orchestrator ใหม่

รับคำถาม → ตรวจ session/สิทธิ์ → ให้ LLM เลือก tool → validate args → เรียก Analytics → เรียบเรียงคำตอบจากผลลัพธ์เท่านั้น

6. Audit Log

บันทึกแบบ append-only: ใครถาม, ใช้ tool อะไร, args ที่ sanitize แล้ว, ขอบเขตสาขา, ผลลัพธ์อ้างอิง, outcome

7. หน้าใช้งาน

Dashboard (Web) และ LINE LIFF — ผู้ใช้เห็นคำตอบพร้อมช่วงเวลา ตัวชี้วัด และข้อจำกัดของข้อมูล

Data Structure for LLM · ชั้นที่ 1

Metric Catalog — นิยามตัวชี้วัดให้ตรงกันก่อนเขียนโค้ด

ถ้าคำว่า “รายได้” หรือ “อัตราการใช้งาน” ยังนิยามไม่ตรงกัน คำตอบของ AI จะเถียงกันเองตลอด

ตัวชี้วัดนิยามหน่วยหมายเหตุ
revenueผลรวมมูลค่ารอบซักที่มีหลักฐานการชำระเงินสตางค์ (จำนวนเต็ม)เก็บเป็น satang ตามโค้ดเดิม กันปัญหาทศนิยม
cycle_countจำนวนรอบซักที่จบสมบูรณ์รอบนับจาก MACHINE_CYCLE ที่มีสถานะจบ
utilizationเวลาที่เครื่องทำงาน ÷ เวลาที่เปิดให้บริการร้อยละต้องระบุเวลาทำการของสาขาให้ชัด
avg_cycle_minutesค่าเฉลี่ยระยะเวลาต่อรอบนาทีใช้ดูความผิดปกติของเครื่อง
peak_hourช่วงชั่วโมงที่มีรอบซักหนาแน่นสูงสุดชั่วโมง 0–23ฐานของข้อเสนอโปรโมชัน (Phase 2)
coinbox_estimateประมาณการเหรียญสะสมในกล่องสตางค์ข้อควรระวัง รีเซ็ตได้จาก event coinbox_open ที่แมปไว้ชัดเจนเท่านั้น ห้ามเดาจาก door_status

กำหนดร่วมทุกตัว: เขตเวลา Asia/Bangkok · ขอบเขตช่วงเวลาแบบ [start, end) · ความละเอียด hour | day | month · และทุก query ต้องผูกกับ branch_id

Data Structure for LLM · ชั้นที่ 2

Pre-aggregated Rollup — สรุปไว้ล่วงหน้า ไม่ให้ LLM แตะข้อมูลดิบ

ข้อมูลดิบระดับ event มีปริมาณมากเกินกว่าจะใส่ context และช้าเกินกว่าจะตอบสด จึงสรุปเป็นตารางระดับ “ชั่วโมง × สาขา × เครื่อง” ไว้ก่อน

  • เร็วและคงที่ — คำถามเดิมได้ตัวเลขเดิมทุกครั้ง ทดสอบด้วย unit test ได้
  • เล็ก — ส่งเข้า LLM เพียงหลักสิบแถว แทนหลักแสน event
  • ปลอดภัย — ชั้นสรุปไม่มีข้อมูลส่วนบุคคล ลดความเสี่ยงข้อมูลรั่ว
  • ต่อยอดง่าย — รวมจากรายชั่วโมงเป็นรายวัน / รายเดือนได้ทันที

แนบ ตัวชี้วัดคุณภาพข้อมูล ไปกับทุกแถว เช่น สัดส่วนชั่วโมงที่ telemetry ขาดหาย เพื่อให้คำตอบบอกข้อจำกัดได้ตรงความจริง 

-- ตารางสรุปรายชั่วโมง (แนวคิด)
TABLE metric_rollup_hourly (
  branch_id        -- บังคับ ใช้คุมขอบเขตสิทธิ์
  machine_id
  bucket_start     -- ต้นชั่วโมง Asia/Bangkok
  cycle_count
  revenue_satang
  runtime_seconds
  open_seconds     -- ใช้หาร utilization
  telemetry_gap_seconds
  PRIMARY KEY (branch_id, machine_id, bucket_start)
)

-- ตัวอย่างข้อมูลที่ LLM จะได้เห็น
{ "branch_id": "BKK-SILOM",
  "bucket_start": "2026-07-01T18:00+07:00",
  "cycle_count": 14,
  "revenue_satang": 84000,
  "utilization_pct": 62.5 }
ชั้นนี้คือ “ภาษากลาง” ระหว่างฐานข้อมูลกับ AI06
Data Structure for LLM · ชั้นที่ 3

Allow-listed Tools — LLM เลือกได้เฉพาะเครื่องมือที่เราสร้างไว้

LLM ไม่ได้รับสิทธิ์เขียน SQL แต่ได้รับ “เมนู” ฟังก์ชันที่ผ่านการทดสอบแล้วเท่านั้น

Toolใช้ตอบคำถามแบบไหน
get_revenue_summaryรายได้รวม/แยกสาขา ในช่วงเวลาหนึ่ง
compare_periodเทียบเดือนต่อเดือน (MoM) ตามตัวอย่างใน R08
get_utilizationอัตราการใช้งานเครื่อง คุ้มค่าหรือไม่
get_cycle_statsจำนวนรอบ เวลาเฉลี่ย ความผิดปกติ
get_peak_hoursช่วงพีคและช่วงว่าง ฐานของ Phase 2

คำถามที่ไม่มี tool รองรับ ระบบตอบว่า “ยังไม่รองรับ” — ดีกว่าเดาแล้วผิด 

// นิยาม argument แบบเข้มงวด (zod / JSON Schema)
get_revenue_summary({
  branch_ids:  string[]   // ต้องเป็นสับเซตของสิทธิ์ผู้ใช้
  period:      { start, end }  // ISO, [start, end)
  granularity: "day" | "month"
  compare_to:  { start, end } | null
})

// ลำดับการตรวจฝั่ง backend (ไม่เชื่อ LLM)
1. parse ด้วย schema — ผิดรูป = ปฏิเสธ
2. branch_ids ∩ สิทธิ์ผู้ใช้ = ขอบเขตจริง
3. ถ้าเซตว่าง = ปฏิเสธ + audit
4. จำกัดความยาวช่วงเวลาและจำนวนแถว
5. query แบบ parameterized เท่านั้น

กติกาเหล็ก: ต่อให้ LLM ขอสาขาที่ไม่มีสิทธิ์ backend จะตัดออกเสมอ — Manager จึงดึงข้อมูลข้ามสาขาไม่ได้ ตามตัวอย่างใน R08

Data Structure for LLM · ชั้นที่ 4

Result Envelope — รูปแบบผลลัพธ์เดียว ที่บังคับให้คำตอบมีที่มา

{
  "scope":    { "branch_ids": ["BKK-SILOM"],
                "granted_by": "role:owner" },
  "period":   { "start": "2026-07-01T00:00+07:00",
                "end":   "2026-08-01T00:00+07:00" },
  "metric":   "revenue",
  "unit":     "satang",
  "rows":     [ ... ],
  "row_count": 31,
  "coverage": { "expected_hours": 744,
                "observed_hours": 731 },
  "caveats":  ["telemetry ขาดหาย 13 ชั่วโมง"],
  "source":   "metric_rollup_hourly",
  "generated_at": "2026-07-31T09:12+07:00",
  "result_ref":   "res_01J..."
}

ทำไมต้องมี unit และ period

บังคับให้คำตอบระบุหน่วยและช่วงเวลาเสมอ ผู้บริหารจึงไม่ตีความผิด และตรงตามเกณฑ์ยอมรับของ R08

ทำไมต้องมี coverage และ caveats

ข้อมูล IoT มีช่วงขาดหายจริง ระบบต้องบอกตรง ๆ ว่าตัวเลขครอบคลุมแค่ไหน แทนที่จะทำเป็นว่าสมบูรณ์

ทำไมต้องมี result_ref

เป็นหมายเลขอ้างอิงผลลัพธ์ที่บันทึกใน audit log ย้อนกลับไปตรวจได้ว่าคำตอบวันนั้นมาจากตัวเลขชุดใด

คำสั่งควบคุม LLM

“ตอบจากผลลัพธ์ของ tool เท่านั้น ห้ามประมาณเอง ถ้าข้อมูลไม่พอให้บอกว่าไม่พอ และต้องระบุช่วงเวลา ตัวชี้วัด และข้อจำกัดทุกครั้ง”

Envelope เดียวกันนี้ใช้กับทุก tool เพื่อให้ทดสอบและตรวจสอบง่าย08
ความปลอดภัยและการตรวจสอบ

สามเสาที่ทำให้อาจารย์ตรวจสอบย้อนกลับได้ทุกคำตอบ

เสา 1 RBAC + Branch Scope

สิทธิ์ถูกตัดสินจาก session ฝั่ง server ไม่ใช่จากสิ่งที่ LLM ขอ ทุก query ผูก branch_id ที่ผ่านการ intersect กับสิทธิ์จริงแล้ว

เสา 2 Append-only Audit Log

บันทึก actor, prompt ที่ sanitize, ชื่อ tool, arguments, ขอบเขต, result_ref, outcome และเวลา — แก้ย้อนหลังไม่ได้ ตาม F-07

เสา 3 Golden-question Eval

ชุดคำถามมาตรฐานพร้อมคำตอบที่รู้ค่าจริง ใช้รันอัตโนมัติเพื่อจับ regression และการหลอนตัวเลข

สถานการณ์ทดสอบผลลัพธ์ที่ระบบต้องทำ
Manager ถามข้อมูลสาขาที่ไม่ได้ดูแลปฏิเสธ ไม่คืนตัวเลขใด ๆ และบันทึก audit ว่าถูกปฏิเสธเพราะขอบเขตสาขา
ถามเรื่องที่ยังไม่มี tool รองรับตอบว่ายังไม่รองรับ ไม่พยายามเดาคำตอบ
ช่วงเวลาที่ถามมี telemetry ขาดหายมากตอบพร้อมระบุความครอบคลุมและข้อจำกัด หรือแจ้งว่าข้อมูลไม่พอ
ถามคำถามเดิมซ้ำสองครั้งได้ตัวเลขเดิม เพราะตัวเลขมาจากฟังก์ชัน ไม่ใช่จากการสร้างข้อความ
นี่คือชุดหลักฐานสำหรับการสาธิตหน้าชั้น09

2สร้างชั้น Rollup รายชั่วโมงตารางสรุป + งานสรุปข้อมูล + unit testตัวเลขตรงกับการนับจากข้อมูลดิบ
