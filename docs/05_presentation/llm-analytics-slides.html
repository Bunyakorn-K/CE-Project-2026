แบบที่ไม่เอา Blackbox

โยนคำถาม + ข้อมูลดิบ (หรือสิทธิ์ query ฐานข้อมูล) ให้ LLM แล้วหวังว่าจะตอบถูก

• ตัวเลข หลอน (hallucination) ตรวจย้อนกลับไม่ได้
• LLM เขียน SQL เอง = ช่องโหว่ข้ามสาขา / ข้ามสิทธิ์
• ข้อมูลดิบยาวเกิน context และเปลืองต้นทุน
• ตอบไม่เหมือนเดิมทุกครั้ง (non-deterministic)
• ไม่มีหลักฐานว่าใครถามอะไร ระบบตอบจากอะไร

ภาพรวมระบบ

ข้อมูลเดินทางจากเครื่องซักผ้า ถึงคำตอบผู้บริหารอย่างไร

ภาพรวมนี้แยก current code ออกจาก target architecture: current มี scope, allow-list, direct reports และ envelope จริง; rollup กับ audit เต็มเป็นขั้นต่อไป

1. Edge / IoT target

Target physical path: Modbus/MQTT → telemetry event; current direct MQTT ingestion is descoped and IRIS is the ingestion boundary

2. Ingestion target

Target semantic model: validate branch/machine and derive MACHINE_CYCLE; current ETL normalizes usage, temperature, and weather into ClickHouse

3. Rollup target

Target: สรุปล่วงหน้าเป็นราย “ชั่วโมง / วัน × สาขา × เครื่อง”; current code ยัง query ClickHouse fact tables โดยตรง

4. Analytics Functions target expansion

Target: semantic layer คืนค่าเป็น envelope มาตรฐาน; current มี MCP allow-list 6 tools และ envelope { meta, data }

5. Assistant Orchestrator ใหม่

รับคำถาม → ตรวจ session/สิทธิ์ → ให้ LLM เลือก tool → validate args → เรียก Analytics → เรียบเรียงคำตอบจากผลลัพธ์เท่านั้น

6. Audit (บางส่วน)

Current local audit ครอบคลุม grant / alert / settings; target คือ prompt + tool + sanitized args + scope + result_ref + outcome แบบ append-only

7. หน้าใช้งาน

Dashboard (Web) และ LINE LIFF — ผู้ใช้เห็นคำตอบพร้อมช่วงเวลา ตัวชี้วัด และข้อจำกัดของข้อมูล

Data Structure for LLM · ชั้นที่ 1

Metric Catalog — นิยามตัวชี้วัดให้ตรงกันก่อนเขียนโค้ด

ถ้าคำว่า “รายได้” หรือ “อัตราการใช้งาน” ยังนิยามไม่ตรงกัน คำตอบของ AI จะเถียงกันเองตลอด

ตัวชี้วัดนิยามหน่วยหมายเหตุ
revenueผลรวมมูลค่ารอบซักที่มีหลักฐานการชำระเงินสตางค์ (จำนวนเต็ม)เก็บเป็น satang ตามโค้ดเดิม กันปัญหาทศนิยม
cycle_countจำนวนรอบซักที่จบสมบูรณ์รอบนับจาก MACHINE_CYCLE ที่มีสถานะจบ
utilizationเวลาที่เครื่องทำงาน ÷ เวลาที่เปิดให้บริการร้อยละต้องระบุเวลาทำการของสาขาให้ชัด
avg_cycle_minutesค่าเฉลี่ยระยะเวลาต่อรอบนาทีใช้ดูความผิดปกติของเครื่อง
peak_hourช่วงชั่วโมงที่มีรอบซักหนาแน่นสูงสุดชั่วโมง 0–23ฐานของข้อเสนอโปรโมชัน (Phase 2)
coinbox_estimateประมาณการเหรียญสะสมในกล่องสตางค์ข้อควรระวัง รีเซ็ตได้จาก event coinbox_open ที่แมปไว้ชัดเจนเท่านั้น ห้ามเดาจาก door_status

กำหนดร่วมทุกตัว: เขตเวลา Asia/Bangkok · ขอบเขตช่วงเวลาแบบ [start, end) · ความละเอียด hour | day | month · และทุก query ต้องผูกกับ branch_id

Data Structure for LLM · ชั้นที่ 2

Pre-aggregated Rollup — target architecture ไม่ใช่ตารางที่ current code มีแล้ว

แนวคิด target คือสรุปข้อมูลดิบระดับ event ให้เล็กและเร็วขึ้น จึงสรุปเป็นตารางระดับ “ชั่วโมง × สาขา × เครื่อง” ไว้ก่อน แต่ current implementation ยัง query ClickHouse fact tables โดยตรง

  • เร็วและคงที่ — คำถามเดิมได้ตัวเลขเดิมทุกครั้ง ทดสอบด้วย unit test ได้
  • เล็ก — ส่งเข้า LLM เพียงหลักสิบแถว แทนหลักแสน event
  • ปลอดภัย — ชั้นสรุปไม่มีข้อมูลส่วนบุคคล ลดความเสี่ยงข้อมูลรั่ว
  • ต่อยอดง่าย — รวมจากรายชั่วโมงเป็นรายวัน / รายเดือนได้ทันที

แนบ ตัวชี้วัดคุณภาพข้อมูล ไปกับทุกแถว เช่น สัดส่วนชั่วโมงที่ telemetry ขาดหาย เพื่อให้คำตอบบอกข้อจำกัดได้ตรงความจริง 

-- ตารางสรุปรายชั่วโมง (แนวคิด)
TABLE metric_rollup_hourly (
  branch_id        -- บังคับ ใช้คุมขอบเขตสิทธิ์
  machine_id
  bucket_start     -- ต้นชั่วโมง Asia/Bangkok
  cycle_count
  revenue_satang
  runtime_seconds
  open_seconds     -- ใช้หาร utilization
  telemetry_gap_seconds
  PRIMARY KEY (branch_id, machine_id, bucket_start)
)

-- ตัวอย่างข้อมูลที่ LLM จะได้เห็น
{ "branch_id": "BKK-SILOM",
  "bucket_start": "2026-07-01T18:00+07:00",
  "cycle_count": 14,
  "revenue_satang": 84000,
  "utilization_pct": 62.5 }

Data Structure for LLM · ชั้นที่ 3

Current MCP Tools — LLM เลือกได้เฉพาะ 6 เครื่องมือที่ server allow-list ไว้

LLM ไม่ได้รับสิทธิ์เขียน SQL แต่ได้รับ “เมนู” ฟังก์ชันที่ผ่านการทดสอบแล้วเท่านั้น

Current toolใช้ตอบคำถามแบบไหน
get_revenue_dailyรายได้และรอบรายวัน; ต้องมี revenue scope
get_cycles_dailyรอบรายวันและ duration เฉลี่ย
get_utilization_heatmapช่วงเวลา/เครื่องสำหรับ utilization
get_temperature_curveอุณหภูมิตามช่วงเวลา ไม่เกิน 5,000 จุด
get_weather_usage_correlationcorrelation เท่านั้น ไม่ใช่ forecast
get_off_peak_windowsbaseline ช่วงว่าง Phase 2

คำถามที่ไม่มี tool รองรับ ระบบตอบว่า “ยังไม่รองรับ” — ดีกว่าเดาแล้วผิด 

// นิยาม argument แบบเข้มงวด (zod / JSON Schema)
get_cycles_daily({
  from:     "2026-08-01"
  to:       "2026-08-31"
  branchId: "b1" // server-bound scope; ไม่มี accessScope argument
})

// ลำดับการตรวจฝั่ง backend (ไม่เชื่อ LLM)
1. parse ด้วย schema — ผิดรูป = ปฏิเสธ
2. server-bound scope = ขอบเขตจริงจาก session/grants
3. ถ้า scope ไม่ผ่าน = ปฏิเสธก่อน query; audit เต็มของ AI ยังเป็น target
4. จำกัดความยาวช่วงเวลาและจำนวนแถว
5. query แบบ parameterized เท่านั้น

กติกาเหล็ก: ต่อให้ LLM ขอสาขาที่ไม่มีสิทธิ์ backend จะตัดออกเสมอ — Manager จึงดึงข้อมูลข้ามสาขาไม่ได้ ตามตัวอย่างใน R08

Data Structure for LLM · ชั้นที่ 4

Result Envelope — รูปแบบผลลัพธ์เดียว ที่บังคับให้คำตอบมีที่มา

{
  "meta": {
    "range": { "from": "2026-08-01", "to": "2026-08-31" },
    "branchId": "b1",
    "dataSource": "real"
  },
  "data": [ ... ]
}

Current envelope มีอะไรบ้าง

meta มี range, branchId, dataSource และบาง tool มี method/rules/caveats; data เป็นแถวผลลัพธ์

Target envelope ที่ยังไม่ ship

Target จะเพิ่ม scope, period, metric, unit, coverage, source, generated_at และ result_ref เพื่อให้ตรวจย้อนกลับได้

ทำไมยังไม่เรียกว่า audit เต็ม

Current schema มี audit สำหรับ grants, alerts, settings; ยังไม่มีตาราง prompt/tool-call/result ที่ครบตาม target

Target system prompt

“ตอบจากผลลัพธ์ของ tool เท่านั้น ห้ามประมาณเอง ถ้าข้อมูลไม่พอให้บอกว่าไม่พอ และต้องระบุช่วงเวลา ตัวชี้วัด และข้อจำกัดทุกครั้ง”

Current `{ meta, data }` ใช้กับทุก tool; richer envelope เป็น target08
ความปลอดภัยและการตรวจสอบ
