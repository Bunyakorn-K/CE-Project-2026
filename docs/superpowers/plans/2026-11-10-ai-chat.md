# AI chat in LINE: what exists, what is missing, and the plan

**Date:** 2026-11-10
**Status:** plan — nothing here is built yet beyond the "today" column.
**Related:** `docs/04_traceability/ops-verification-2026-11-09-ai-audit.md`,
`apps/api/src/bot/*`, `apps/api/src/llm-client.ts`

## 1. What exists today (measured, not remembered)

| piece | where | state |
|---|---|---|
| Webhook + signature check | `bot/index.ts`, `index.ts` `/webhooks/line` | works, verified 2026-11-09 |
| Identity from LINE id → grants → scope | `bot/identity.ts` | works; scope derived server-side, never from the user's claim |
| LLM call, DB-driven gateway/key/model/prompt | `conversation.ts` → `llm-client.ts` | works; `ai_settings` row, editable in `/admin/ai` |
| Tools | MCP server over Streamable HTTP, scope signed in a header | works; **`maxSteps: 2`** = one tool round-trip |
| Audit | `runAuditedToolCall` → `audit_log` with args digest | works, one row per call, success and failure |
| Reply vs push | `LineAdapter.sendText(..., {replyToken})` | works; reply is free, push is charged |
| Answer delivery | webhook acks immediately, answer sent async via `reply()` with the token, push only if the reply is rejected | **measured today**: 3 chat answers, and LINE's quota consumption stayed at 17 — exactly the 17 alert pushes. The answers cost nothing, so every one went out as a reply |
| Chat history | `chat_message` table — **playground only** | the LINE bot has none |
| Events handled | text messages only | no follow, unfollow, postback, beacon |
| Rich menu | four panels, per role, `แชทกับ AI` sends `"สวัสดี"` | live 2026-11-10 |

So: **the bot answers single questions well.** It is not yet a chat.

## 2. The gaps, in the order a user feels them

1. **No memory.** Every message is `input: ctx.userText` with no history. "แล้วเดือนที่แล้วล่ะ" gets an answer about nothing. This is the single biggest difference between "ask the bot" and "chat".
2. **No acknowledgement while thinking.** The user taps, sees nothing for 3–10 seconds, and taps again. LINE has a free typing indicator (`showLoadingAnimation`, 5–60s) that we never call.
3. **A second message is dropped silently.** `busy` is a `Set`: if a user sends two messages while the first is in flight, the second is discarded with no reply at all.
4. **One tool round-trip.** `maxSteps: 2` means the model may call one tool and answer. "เทียบสาขา A กับ B" needs two calls and cannot.
5. **Long answers get truncated by LINE, not by us.** Text messages cap at 5,000 characters and a reply can carry at most 5 messages. Nothing shapes or splits the output.
6. **No quick replies / no help.** The user has no idea what the bot can answer, so they type "สวัสดี" and stop.
7. **No postback handling.** Any future button (ยืนยัน / ยกเลิก / เลือกสาขา) has nowhere to arrive, so every confirmation has to be a typed word.
8. **No follow/unfollow handling.** A new follower gets silence; nothing records that they arrived.
9. **No chat-side quota guard.** Replies are free, but every fallback push is charged, and there is no per-user rate limit — one enthusiastic user can spend the month's allowance in an afternoon.
10. **No answer-level observability.** The audit covers tool calls; nothing records "this question, this model, 4 steps, 9.2s, 1,100 characters, pushed".

## 3. Decisions to make (with a recommendation each)

### D1. Where does conversation memory live?

**Recommendation: a `chat_turn` table in SQLite, last 8 turns (user + assistant) per LINE user, 30-day retention.**

Alternative considered: keep the conversation in the model prompt only (stateless). Rejected because a question about "last month" needs the previous turn to resolve which month.

The store must be scoped per LINE user, not per account: a person who is a manager on two branches has two scopes in one identity, and the memory follows the person.

Why a table and not memory-of-process: the container restarts on every deploy, and an in-memory history would silently reset mid-conversation.

Retention mirrors `chat_message` (30 days via the existing purge job) — the same reasoning: enough to answer follow-ups, short enough that a "who asked what" table does not become a second copy of the shop's data.

### D2. Typing indicator?

**Recommendation: yes, on receipt, `showLoadingAnimation(userId, 20)`.** It is free, it covers the LLM latency, and it is the difference between "it is thinking" and "it is broken".

### D3. Reply or push for the answer?

**Recommendation: keep the current reply-first path — it is already working — and record which path fired.**

Measured today rather than assumed: LINE reports 17 messages consumed, which is exactly the 17 alert pushes; the three chat answers cost nothing, so they went out as replies. The reply token lives 60 seconds and a tool round-trip fits comfortably.

What is missing is the record: `chat_turn` gains `delivered: "reply" | "push"`, so the day the loop starts outliving the window it is visible instead of being discovered when the alert budget runs out early.

### D4. How many messages may one answer send?

**Recommendation: at most 2 text messages, and a prompt instruction to stay under 900 characters.**

A 5-message wall is not a chat answer, it is a document. Long detail belongs behind a LIFF link, exactly like the alert cards: the chat says the headline and offers the page.

### D5. Does the bot ever *do* something, or only read?

**Recommendation: read + one confirmation action, nothing else, for now.**

The MCP surface is read-only by design. The one write worth having in chat is **acknowledging an alert** ("รับทราบ alert ล่าสุด" → postback → the same `alert_acknowledgement` row the web writes), because it is the action people take from a phone. Everything else (revoking access, changing settings) stays in the backoffice where the consequences are visible.

### D6. Rate limit and quota guard?

**Recommendation: 20 messages per hour per LINE user, 300 per day across all users; both refused with a Thai sentence that says so.**

The LLM is the cost here, not LINE. A shared daily cap also protects the fallback pushes.

### D7. Which model?

**Recommendation: keep whatever `/admin/ai` says; do not hardcode.** The plan adds a `maxSteps` setting beside it (`4` default), because "how many tool calls may one answer make" is the same kind of operational knob as the model.

## 4. Phases

Each phase ships alone, is verifiable from outside, and leaves the system working.

### P1 — a conversation instead of a question (highest value, lowest risk)

- `chat_turn` table + `bot/memory.ts`: `appendTurn(userId, user, assistant)`, `recentTurns(userId, limit=8)`, purge with the existing 30-day job.
- `conversation.ts` feeds the turns as prior messages, and the system prompt gains one line: answers are short, and "the last three questions" are available.
- `showLoadingAnimation` on receipt (before the MCP/LLM work starts).
- Replace the `busy` Set with a one-slot queue per user: the second message waits for the first, then answers in order. Dropping is worse than being late.
- `maxSteps: 2 → 4`, exposed in `ai_settings`.

**Acceptance:** ask "ภาพรวมวันนี้เป็นยังไง" then "แล้วเมื่อวานล่ะ" — the second answer covers yesterday without restating the subject. Two messages sent in quick succession both get answers, in order. A typing indicator appears within a second. `chat_turn` shows 4 rows with `delivered` values.

### P2 — the bot can be talked to, not just asked

- Postback handler + typed payloads (`ack:<alertId>`, `branch:<id>`, `help`).
- `รับทราบ` via postback writes an acknowledgement and answers with what changed.
- Quick replies on the first message of a conversation: "ภาพรวมวันนี้", "เครื่องที่มีปัญหา", "แจ้งซ่อม".
- Follow event → welcome message (carries a reply token, so it is free) naming what the bot can answer.
- A `help` answer listing three example questions per role from the same definitions the rich menu uses.

**Acceptance:** a new follower gets one welcome message; "ช่วยอะไรได้บ้าง" answers with role-appropriate examples; tapping รับทราบ on an alert card in chat creates the acknowledgement row and the reply says so.

### P3 — it cannot surprise us

- Answer shaping: ≤ 900 characters, ≤ 2 messages, split on paragraph boundaries, never mid-word.
- `chat_turn` gains `model, steps, tool_calls, latency_ms, chars, delivered, tokens` — the observability the audit does not cover. `delivered` is the field that shows a reply turning into a push.
- Rate limit (D6) and a daily push counter, both surfaced in `/admin` beside the alert budget.
- A `CHAT_ENABLED` switch, so chat can be turned off without a deploy when the gateway is down.

**Acceptance:** a 5,000-character answer arrives as two messages, both under the cap; the 21st message in an hour is refused in Thai; `/admin` shows today's chat count and the reply/push split.

### P4 — optional, only if P1–P3 are used

- A daily digest as a chat message instead of only an alert card (one message, plain language).
- Remembered preferences ("สาขาของฉัน" resolved once by postback, not every time).

## 5. Risks

| risk | consequence | mitigation |
|---|---|---|
| Memory grows without a purge | SQLite bloat, slow answers | reuse the 30-day purge; cap rows per user |
| Postback payloads are user-forgeable | someone acks an alert they cannot see | re-check the scope server-side on every postback, exactly as the HTTP route does |
| Model answers with another branch's numbers | trust loss | already structurally prevented (scope signed into MCP); test it with a technician identity |
| The push fallback quietly eats the alert budget | alerts stop near month end | count chat pushes against the same monthly budget and show both in `/admin` |
| A long answer arrives as 5 messages | reads as spam | cap at 2, plus the LIFF link pattern |

## 6. Open questions for the owner

1. **Memory depth** — 8 turns is my default. Longer memory costs tokens per message; 8 keeps a typical answer under ~2k tokens.
2. **Acknowledge from chat** — is รับทราบ in LINE something your staff should be able to do, or should it stay a web-only action?
3. **Digital receipt / daily digest** — P4 only matters if you want the bot to speak first. Do you?
4. **Language** — Thai only, or should the assistant answer English questions in English? (The prompt is Thai-first today.)
