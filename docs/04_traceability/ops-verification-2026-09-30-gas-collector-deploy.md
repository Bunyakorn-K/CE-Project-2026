# Ops verification — gas-pressure collector deployment (2026-09-30)

**Scope:** deploying the `otterimju2` gas-pressure collector, the first load into
`fact_gas_pressure_sample`, and the first production data from the Home Assistant
source. Companion to `docs/03_data_contracts/ha_gas_sensor_contract.md` (the
contract) and `apps/etl/src/gas.ts` (the code).

**Status: deployed and verified.** Local test evidence (26 unit tests, DDL and
idempotency executed on a real ClickHouse engine, a 50,567-row replay of the real
export with zero rows dropped) preceded this; this record is the production
evidence.

## 3. The six steps, and what each one actually required

The planned sequence was: create table → provision the HA token → write
`gas.env` → build the image → `compose --profile gas up -d` → smoke test. Three
of those turned out to be incomplete as written. Each correction is recorded
below rather than folded silently into the plan.

### 3.1 `CREATE TABLE` — as planned

Applied from the DDL generated by `apps/etl/src/schema.ts` (not transcribed by
hand). `SHOW CREATE TABLE` after the change matches the declaration
character-for-character, including the `Enum8` numbering and
`ReplacingMergeTree(ingested_at)`. Row count immediately after: `0`. No other
table in `laundrytwin_analytics` changed.

### 3.2 HA token — the blocker did not materialise

The plan assumed a new long-lived access token had to be minted, and that
Home Assistant's removal of the password grant would make that a UI-only,
operator-blocked step. That assumption was wrong in a useful way: a token
already existed at `/tmp/otterimju2-ha-test-token` from earlier reconnaissance
and still authenticates (`GET /api/` → `200`). It was transferred to the host
over `ssh` **stdin**, so it never appeared in a command line, in the remote
process table, or in this repository. Written into `gas.env` at mode `0600`.

The token is a credential for the shop's Home Assistant instance. It lives only
in `gas.env` on VM 117 and in the operator's local `/tmp`. It is not in git, not
in tofu state as plaintext, and is not in any rendered artifact in the
repository.

### 3.3 `gas.env` — built on the host, never through a terminal

The `CLICKHOUSE_*` writer credential was extracted **on the host** from the
running `laundrytwin-weather-1` container, so the password never crossed the
wire or appeared in a process table. The HA token was the only value piped in
from the Mac, over stdin.

Verified: mode `0600`; exactly the ten expected keys
(`CLICKHOUSE_URL`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`,
`CLICKHOUSE_DATABASE`, `HA_BASE_URL`, `GAS_TENANT_ID`, `GAS_BRANCH_ID`,
`GAS_BRANCH_SLUG`, `GAS_LOOKBACK_HOURS`, `HA_TOKEN`); **no**
`PG_CONNECTION_STRING`; token length 183 as expected.

`GAS_LOOKBACK_HOURS=3` against an hourly loop means each pass overlaps two
previous ones. The table is `ReplacingMergeTree(ingested_at)`, so the overlap
converges to one row — proven in §3.6.

### 3.4 Image build — the plan's build command was wrong on this host

The first image was built on an Apple Silicon Mac and produced an `arm64`
image. The deploy host is `linux/amd64` and has **no binfmt emulation**, so the
container could not start:

```text
exec /usr/local/bin/docker-entrypoint.sh: exec format error
```

with `RestartCount` climbing (observed at 4) under `restart: unless-stopped`.
The container was stopped and the image rebuilt with
`--platform linux/amd64`, then transferred to the host as a
`docker save | gzip | ssh … docker load` stream (the Mac holds no credential for
the registry, and the host's registry listener requires htpasswd auth).

**This is a standing trap, not a one-off.** The `apps/etl/Dockerfile` header
documents the build commands without a platform flag, and every other LaundryTwin
image in the registry is `amd64`. Any future build from an arm64 workstation
reproduces this failure. The fix is recorded in the Dockerfile header; the
`--platform linux/amd64` flag is required when building from a non-amd64 host.

### 3.5 Start — a sixth step the plan did not contain

The first start failed:

```text
Code: 497. DB::Exception: etl_writer: Not enough privileges.
To execute this query, it's necessary to have the grant INSERT ON
laundrytwin_analytics.fact_gas_pressure_sample. (ACCESS_DENIED)
```

Creating a table under `etl_writer` does not grant that user rights on it. The
grants were read off the sibling fact tables and copied exactly:

```sql
GRANT INSERT       ON laundrytwin_analytics.fact_gas_pressure_sample TO etl_writer;
GRANT CREATE TABLE ON laundrytwin_analytics.fact_gas_pressure_sample TO etl_writer;
```

`SELECT` was deliberately **not** granted: no fact table grants it to
`etl_writer`, and the collector never reads this table. Least privilege is
preserved.

Any new table added to this warehouse needs this grant step. It is invisible from
the code — the DDL is applied by `etl_writer` itself and the failure only
surfaces at the first INSERT.

### 3.6 Smoke test

First successful pass:

```text
Gas collection: 884 rows over 2026-09-30 10:35:45.284 .. 2026-09-30 13:35:45.284
(0 unavailable, kept as NULL)
```

Verified in the warehouse:

| Check | Result |
|---|---|
| Rows per channel | `gas_run_a_pressure` 97, `gas_run_b_pressure` 343, `changeover_filter_pressure` 444 |
| Recorded range | `10:35:45.284` → `13:35:18.846` — matches the log line exactly |
| psi range | run A 17–21, run B 87–111, changeover 15–21. **No 0 anywhere** |
| Branch binding | exactly one `(tenant, branch, slug)` triple: `9069c13d-…`, `5e9611c1-…`, `otterimju2` |
| `value_psi = 0` rows | **0** |
| `unavailable`/`unknown` coerced to a number | **0** |
| Distinct `entity_id` | exactly the three allow-listed; **no `gas_detector`** |
| Raw rows vs distinct keys | 884 vs 884 — no inflation |

**Idempotency, measured rather than asserted.** The collector was restarted to
force a second pass over an overlapping window:

| | |
|---|---|
| Before | 884 rows |
| After second pass (raw, unmerged) | 1,769 rows |
| Distinct `(tenant, branch, channel, recorded_at)` | 895 |
| After `OPTIMIZE TABLE … FINAL` | **895** |

Raw rows doubled as expected for an overlapping re-read; the merge collapsed
them to the distinct set with no inflation. This is the property the 3-hour
lookback depends on, and it is now observed rather than assumed.

Other services were untouched by the deploy: `laundrytwin-weather-1` (21h),
`laundrytwin-etl-1` (21h), `laundrytwin-api-1` (25h), `laundrytwin-web-1` (26h)
all kept their original uptime.

## 4. Incidental finding: the weather env split had never been deployed

`/opt/laundrytwin/compose.yaml` on the host was still the **pre-split** version,
in which `weather` used `env_file: ${ETL_ENV_FILE:-/opt/laundrytwin-etl/.env}`.
That is why the running `laundrytwin-weather-1` carries a `PG_CONNECTION_STRING`
and four `ETL_*` variables it cannot use: it was handed the ETL's env file, not
its own. The split exists in the repository and had simply never been applied.

This blocked the gas deploy: copying the repository's `compose.yaml` over the
host's would have pointed `weather` at `/opt/laundrytwin/weather.env`, which did
not exist, and compose validates every service's `env_file` at parse time — so
`--profile gas up -d gas` would have failed outright.

`/opt/laundrytwin/weather.env` was therefore rendered on the host, matching
`deploy/tofu`'s `weather_env` template exactly (`TMD_API_KEY` plus
`CLICKHOUSE_*`, and no `PG_CONNECTION_STRING`), and the repository's
`compose.yaml` was installed. **The weather container was not recreated**, so it
keeps running with its old environment; it picks up the split env file the next
time it is recreated. Until then the over-broad grant persists in that one
container.

## 5. Remaining drift between the host and the repository

`/opt/laundrytwin/.env` is still rendered from an older tofu template. It lacks
`LAUNDRYTWIN_DEV_BYPASS`, `VITE_LIFF_ID` and `LINE_LOGIN_CHANNEL_ID`, which the
current `app_env` template writes. The three keys this deploy needed
(`GAS_IMAGE`, `GAS_ENV_FILE`, `WEATHER_ENV_FILE`) were added idempotently, so a
future `tofu apply` converges rather than fights.

## 6. Safety boundary — unchanged by this deployment

This is a pressure **trend** source, not a leak detector. No alert is raised
from it, nothing in the Digital Twin or the cycle/revenue KPIs derives from it,
and it must never be represented as a life-safety system. The
`gas_detector_*` entities remain structurally excluded: a test asserts
`GAS_CHANNELS` contains no such entity, so they cannot be ingested by widening
the list. Full reasoning in
`docs/03_data_contracts/ha_gas_sensor_contract.md`.
