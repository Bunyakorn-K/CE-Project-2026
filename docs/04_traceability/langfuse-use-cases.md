# Langfuse ในระบบนี้: ใช้ทำอะไรได้จริง

ก่อนเลือกว่าจะติดตั้งหรือไม่ — เอกสารนี้ตอบว่า LaundryTwin จะ**ใช้** Langfuse ทำอะไรได้
ไม่ได้ตอบว่า Langfuse ดีแค่ไหน

## 1. LLM call ในระบบนี้มีที่ไหนบ้าง

| ที่ | เรียกโมเดล | บันทึกวันนี้ |
|---|---|---|
| บอท LINE (`bot/conversation.ts`) | ทุกข้อความที่ผู้ใช้ถาม | `chat_turn`: model, steps, tool_calls, latency, delivered + ข้อความ |
| AI console test chat (`/admin/ai`) | ตอนเจ้าของกดทดสอบ | `chat_message` (thread) |
| alert sweep (`alert-engine.ts`) | **ไม่เรียก** | `alert_notification`, `audit_log` |
| daily digest (`digest.ts`) | **ไม่เรียก** — ประกอบจาก SQL | `digest_sent` |
| ETL / Airflow | **ไม่เรียก** | Airflow logs |

→ Langfuse มีขอบเขตแค่ **2 ที่แรก** ที่เหลือเป็น deterministic ทั้งหมด และไม่ควรเอา
Langfuse ไปยัดใส่

## 2. สิ่งที่รู้อยู่แล้ว และสิ่งที่ยังไม่รู้

`chat_turn` วันนี้เก็บ: model, จำนวน step, จำนวน tool call, latency รวม, สถานะการส่ง
`audit_log` เก็บ: ชื่อ tool ที่ถูกเรียก, digest ของ args, ผล ok/error (ไม่เก็บค่า args)

| คำถาม | ตอบได้วันนี้ไหม | เพราะอะไร |
|---|---|---|
| คำตอบนี้ใช้กี่ step / กี่ tool | ✅ | `steps`, `tool_calls` |
| ช้ากี่วินาที | ✅ | `latency_ms` |
| คำตอบฟรีหรือเสียโควตา | ✅ | `delivered` |
| **ช้าตอนไหนของงาน** (step ไหน, tool ไหน) | ❌ | มีแต่ผลรวม |
| **กินกี่ token / กี่บาท** | ❌ | ไม่มีการอ่าน `usage` จาก response เลย |
| **tool ไหนให้ข้อมูลที่ทำให้ตอบผิด** | ❌ | audit มีชื่อ tool แต่ไม่ผูกกับ turn |
| **เปลี่ยนโมเดลแล้วดีขึ้นจริงไหม** | ❌ | ไม่มีชุดคำถามมาตรฐานและไม่มีคะแนน |
| **ผู้ใช้พอใจไหม** | ❌ | ไม่มี feedback จาก LINE |
| prompt เวอร์ชันไหนให้ผลอะไร | 🟡 | `prompt_version` อยู่ใน span attribute แล้ว แต่ยังไม่มีที่ให้ดูย้อนหลังหลายสิบครั้ง |

## 3. ถ้าเอา Langfuse มาใช้ จะได้อะไรเป็นรายข้อ

| ความสามารถของ Langfuse | ใช้กับระบบนี้อย่างไร | ต้องเพิ่มอะไรก่อน |
|---|---|---|
| **Traces / spans** | เห็นเส้นทางของคำตอบ: tool ไหนถูกเรียกก่อน-หลัง ใช้เวลาท่าไหน | span ต่อ tool call (ตอนนี้มี span ครอบทั้งคำตอบ) |
| **Sessions** | รวมบทสนทนาของ LINE user หนึ่งคนเป็นเรื่องเดียว (memory 8 เทิร์นมีอยู่แล้วใน DB แต่ดูเป็นภาพไม่ได้) | ผูก `lineUserId` เป็น sessionId + `userId` (เก็บเป็น hash ไม่ใช่ id ดิบ) |
| **Token / cost** | รู้ว่าคำถามแบบไหนแพง และเดือนนี้จ่ายเท่าไร | อ่าน `usage` จาก `streamText` แล้วเก็บ — **ยังไม่มีเลย** และ span ปัจจุบันก็ไม่มี |
| **Model comparison** | เปลี่ยน base URL/model ใน `/admin/ai` แล้วเทียบผลก่อนปล่อยจริง | ชุดคำถามมาตรฐาน (golden set) + การรันซ้ำ + คะแนน (datasets/experiments) |
| **Scores / annotation** | ให้คนกด 👍/👎 ใน LINE หรือให้เจ้าของให้คะแนนคำตอบในคอนโซล | ช่องทาง feedback + การส่ง score กลับ |
| **Prompt management** | รวมศูนย์ prompt | **ไม่แนะนำ**: กฎความปลอดภัยของเราอยู่ในโค้ดและมี test คุม (`REQUIRED_GUARDRAILS`) การย้ายไป UI ทำให้ขอบเขตนั้นหลุด |
| **Alerts on latency/error** | เตือนเมื่อบอทช้าผิดปกติ | ต้องมี span ก่อน (L0 พร้อมแล้ว) |

## 4. สิ่งที่ Langfuse **ไม่** ช่วยในระบบนี้

- การส่งแจ้งเตือนทาง LINE (โควตา 300, cooldown, เพดาน) — เป็นตารางของเรา
- คุณภาพข้อมูลใน ClickHouse / ETL / digest
- ต้นทุนข้อความ LINE (คนละเรื่องกับต้นทุน token)
- สิทธิ์การเข้าถึงสาขา — เป็น `access-grant` ไม่ใช่เรื่องของ tracing

## 5. สามระดับของการเอาไปใช้

| ระดับ | ได้อะไร | งาน | ต้องมี Langfuse ไหม |
|---|---|---|---|
| **L0 (ทำแล้ว)** | span ต่อคำตอบ: model, steps, tool_calls, latency, prompt version, error | เสร็จ (`fa92344`) | ไม่ — OTLP ส่งที่ไหนก็ได้ |
| **L1** | + span ต่อ tool call, + token/cost, + session ต่อ LINE user | ~ครึ่งวัน | ไม่จำเป็น — เก็บลงตาราง `ai_trace` ของเราเองได้ |
| **L2** | + golden set 20 คำถามจริง, รันเทียบโมเดลก่อนสลับ, คะแนน, feedback 👍/👎 จาก LINE | 1–2 วัน | **คุ้มก็ต่อเมื่อถึงขั้นนี้** — UI, การเทียบ run และคะแนนคือสิ่งที่เขียนเองแพง |
| **L3** | self-host Langfuse | ต้องเพิ่ม disk ก่อน | ยังไม่ไหว: ต้อง 16 GiB/100 GiB, เครื่องมี 11 GiB และเหลือ 6.7 GiB |

## 6. ข้อสรุปที่ตรงไปตรงมา

Langfuse ไม่ได้ทำให้บอทตอบเก่งขึ้น และไม่ได้แทนตารางที่เรามีอยู่ — มันตอบคำถามคนละชุด
คำถามที่มันตอบได้และเราตอบไม่ได้ตอนนี้คือ **"เปลี่ยนโมเดล/prompt แล้วดีขึ้นจริงหรือแย่ลง"**
ซึ่งเป็นปัญหาที่เพิ่งเกิดจริงเมื่อ 2026-11-10 (เปลี่ยน gateway แล้วได้คำตอบผิดวัน)

ดังนั้นการตัดสินใจที่ถูกคือเลือกจากสองข้อนี้:

1. **ยังไม่ติดตั้ง** — ทำ L1 เก็บ span ลง SQLite ของเราเอง (ไม่มีข้อมูลออกนอกเครื่อง)
   แล้วค่อยไป Langfuse เมื่อต้องการทำ L2
2. **Langfuse Cloud Hobby (ฟรี)** — เริ่มที่ L1 ส่ง metadata-only ขึ้นไป แล้วทำ L2 ต่อทันที
   เพราะ datasets/experiments ต้องมีที่เก็บ run

ทั้งสองข้อใช้โค้ดชุดเดียวกัน (`telemetry.ts`) ต่างกันที่ `OTEL_EXPORTER_OTLP_ENDPOINT`
